# Plugin API 1.5 Design

## Status

Approved design. API 1.5 is a breaking rewrite; API 1.4 and earlier plugins are not compatible.

## Goals

- Replace fixed plugin UI slots with plugin-provided CSS and script capabilities.
- Run desktop plugins as independently managed processes connected through local versioned JSON-RPC.
- Add plugin pages to the main and settings navigation, including nested navigation.
- Expose controlled file, Internet, page-state, window, DOM, and core-observation APIs.
- Add blocking hooks before every core operation.
- Preserve host ownership of the fairness-critical algorithm and data.

## Non-goals and Accepted Risks

- API 1.5 does not prevent a plugin with `system:execute` from invoking arbitrary system programs. Such a plugin can potentially modify application files, inject processes, or control the operating system using its user account.
- Plugins with DOM and unrestricted CSS access can hide controls or display false text. The application guarantees data integrity at the core boundary, not visual integrity while an untrusted plugin is enabled.
- Web does not emulate desktop process, executable, or complete window capabilities. Unsupported capabilities return structured `UNSUPPORTED_PLATFORM` results.

## Architecture

### Plugin package

The manifest must explicitly declare `api: "1.5"`, process entry points, pages, navigation locations, permissions, file scope, Internet requirement, window capabilities, and operation hooks. JavaScript/TypeScript is supported directly. Other supported languages may provide executable entries through the declared process contract.

### Plugin host

The application owns installation validation, signature status, unsigned-plugin confirmation, load order, process launch and termination, JSON-RPC authentication, permission checks, request timeouts, audit records, and cleanup. A plugin process failure revokes its session and cleans up its pages, windows, hooks, and injected styles.

Signed plugins may use the normal installation flow. Unsigned plugins require an installation confirmation that displays their complete requested permissions and capabilities.

### Process and transport

Each desktop plugin runs in its own process. The host creates an authenticated local JSON-RPC channel with a random session credential. Every request carries the plugin identity, process instance identity, request ID, API version, and permission context. The host applies timeouts, validates arguments and results, and reclaims the process on disconnect.

The plugin owns its page and window lifecycle. The host supplies the underlying handles and performs forced cleanup when the plugin is disabled, exits, or loses its RPC session.

### Web degradation

Web may load plugin pages, navigation, CSS/DOM contributions within browser limits, and ordinary page-state capabilities. Desktop process execution, arbitrary system programs, complete local file access, and window management are unavailable and must not prevent application startup.

## SDK Surface

The 1.5 SDK exposes explicit capability groups rather than the 1.4 compatibility request surface:

```ts
interface PluginApi {
  lifecycle: {
    on(event: PluginEvent, handler: EventHandler): Unsubscribe
    before(operation: CoreOperation, handler: BeforeHandler): Unsubscribe
  }
  page: {
    register(definition: PluginPage): PageHandle
    open(pageId: string, options?: OpenPageOptions): Promise<void>
    close(pageId: string): Promise<void>
  }
  window: {
    create(options: PluginWindowOptions): Promise<PluginWindow>
    close(windowId: string): Promise<void>
    focus(windowId: string): Promise<void>
    main: MainWindowControl
    floating: FloatingWindowControl
  }
  dom: {
    query(selector: string, surface?: 'main' | 'settings'): Promise<DomSnapshot[]>
    read(target: DomTarget, property: string): Promise<unknown>
    write(target: DomTarget, property: string, value: string): Promise<void>
    insert(target: DomTarget, html: string, position?: InsertPosition): Promise<void>
    execute(surface: 'main' | 'settings', script: string, args?: unknown[]): Promise<unknown>
  }
  style: {
    inject(css: string, options?: StyleOptions): Promise<StyleHandle>
    remove(styleId: string): Promise<void>
  }
  files: {
    list(path?: string): Promise<FileInfo[]>
    read(path: string, options?: ReadOptions): Promise<Uint8Array>
    write(path: string, data: Uint8Array | string): Promise<void>
    execute(path: string, args?: string[]): Promise<ProcessResult>
  }
  net: {
    fetch(input: string, options?: NetRequestOptions): Promise<NetResponse>
  }
  pageState: {
    read(scope?: PageStateScope): Promise<unknown>
    write(scope: PageStateScope, patch: Record<string, unknown>): Promise<void>
  }
  core: {
    names: { read(query?: NameQuery): Promise<NameSnapshot> }
    records: { read(query?: RecordQuery): Promise<RecordSnapshot> }
    statistics: { read(): Promise<StatisticsSnapshot> }
    fairness: { read(): Promise<FairnessSummary> }
  }
}
```

The exact TypeScript declarations and JSON-RPC method names are implementation deliverables, but must preserve these ownership and permission boundaries.

## Permissions

Permissions are independently declared and independently displayed to the user. At minimum API 1.5 defines:

- `files:app:read`, `files:app:write`, and `files:app:execute` for the application data directory.
- `files:external:read`, `files:external:write`, and `files:external:execute` for explicitly declared external directories.
- `net:internet` for unrestricted HTTP/HTTPS access through the host network broker.
- `page:read`, `page:write`, and `page:write-sensitive` for page information and state.
- `dom:main`, `dom:settings`, and `style:host` for host DOM and CSS access.
- `window:create`, `window:main:control`, `window:floating:control`, and `window:always-on-top`.
- `core:names:read`, `core:records:read`, `core:statistics:read`, and `core:fairness:read`.
- `core:before-operation` for blocking hooks and filter changes.
- `system:execute` for arbitrary system programs.

The application data directory may be exposed as a whole through the file API, but protected core roots are always denied by the host's canonical-path checks. The protected roots include the algorithm implementation/state, original list storage, random state, history storage, and statistics storage. Path traversal, symlink escapes, and non-canonical paths are rejected.

`net.fetch` is brokered by the host, permits HTTP/HTTPS without a domain allowlist, and applies connection timeout, response-size, redirect, and concurrency limits.

Window control is separated by target. `window:main:control` includes minimize, maximize, restore, resize, move, focus, and close of the main window.

## Navigation and Pages

Plugins may contribute pages to the main navigation and settings navigation. Both locations support first-level and second-level entries. Native navigation entries always come first. Plugin entries are then ordered strictly by plugin load order, followed by declaration order within each plugin manifest. No user or manifest numeric ordering overrides this rule.

Plugins can manage their own page and window lifecycle. The host still removes all contributions and forcibly closes related resources during deactivation.

## CSS and DOM

Plugins may inject arbitrary CSS into the main and settings surfaces and may use arbitrary CSS within their own pages and windows. Host CSS is not restricted to the old component target whitelist.

With the appropriate DOM permissions, plugins use `dom` RPC to query, read, write, insert, and execute JavaScript in the main or settings surface. Errors are returned to the requesting RPC and do not directly crash the host process.

The host must provide a safe-mode launch path that starts without loading plugins, removes injected styles, and restores a trustworthy native UI.

## Page Information and State

Plugins may read page information from the main and settings surfaces. Ordinary page state is readable and writable, including language, theme, animation, display, and draw-filter form state.

Sensitive state is excluded from ordinary writes. Plugin enablement, permission grants, list management, data import/export, history clearing, fairness settings, and window security settings require a separate permission or explicit user confirmation. Host writes must use field allowlists, type validation, and normal store actions.

## Core Operations and Fairness

The Rust core exclusively owns the fairness-critical algorithm, random source/state, list contents and candidate construction, true operation results, history, statistics, and their persistent writes. Plugins can read list snapshots, records, statistics, and the public fairness summary when granted the corresponding read permissions.

The data flow is:

```text
plugin before-operation hooks
  -> host validates and serially merges filter changes
  -> Rust core validates the final operation input
  -> Rust core executes algorithm and random selection
  -> Rust core commits the true result, statistics, and history
  -> host broadcasts after-operation
```

Hooks cover name draw, card flip, lottery draw, prize assignment, and related core operations. Hooks execute serially in plugin load order. Each plugin receives the prior plugin's accepted non-fair filter changes.

Hooks may modify draw filters such as list ID, count, gender, and duplicate policy. The host and Rust core revalidate these fields. Hooks may not submit or modify algorithm selection, random source/state, list contents, candidate sets, true results, history, statistics, or any persistent core data.

Each hook declares a requested timeout. The host applies the lower of the declaration and the operation-specific hard ceiling. Rejection, exception, process exit, timeout, invalid response, or conflicting invalid data aborts the core operation and identifies the failing plugin. There is no partial core commit.

The core commit protocol must reject plugin-supplied records, statistics, algorithm state, random values, candidate lists, and result payloads. If protected data integrity checks detect external modification, the core refuses to perform a draw and reports recovery-required status.

## Migration

- Set the host and SDK version to `1.5.0`.
- Require an explicit `api: "1.5"` manifest declaration.
- Do not load API 1.4 or earlier plugins. Keep their installation records and show a migration-required status.
- Remove the 1.4 compatibility principal and request surface, fixed-slot runtime paths, old component style whitelist, and old iframe runtime when replaced by the new implementation.
- Publish the 1.5 SDK declarations and JSON-RPC protocol documentation for JS/TS and other supported languages.

## Acceptance Tests

Tests must cover:

- Manifest API version, signature status, unsigned-plugin confirmation, and migration display.
- Process launch, authenticated JSON-RPC, disconnect, timeout, crash recovery, process termination, and duplicate request handling.
- Every permission's allow, deny, audit, and Web degradation behavior.
- Canonical-path enforcement, traversal/symlink escape rejection, protected-root denial, and explicit `system:execute` risk behavior.
- CSS injection, DOM query/read/write/insert/execute, main/floating/plugin window control, and cleanup.
- Main/settings first-level and second-level navigation with native-first and load-order sorting.
- All core-operation hooks, serial filter updates, valid and invalid filter changes, rejection, timeout, exception, and rollback behavior.
- Rust-core rejection of plugin attempts to supply or alter algorithm, random state, list contents, candidate sets, results, history, or statistics.
- External protected-data modification detection and draw refusal.
- Roller, Card, Lottery, Records, Lists, and Settings regression flows without plugins and with ordinary API 1.5 plugins.
